# Backend Migration Rules for Notrelix

## Critical Rule: Always Ask Before Creating Migrations

**NEVER auto-generate migrations without explicit user confirmation.**

When EF configuration changes:

1. **Ask first.** Always confirm with the user before running `dotnet ef migrations add`.
2. **Propose a descriptive name.** Use feature-based names like `AddMessagingProcessedEventStatusFields`, not generic names like `Migration1`, `Update`, or `Fix`.
3. **Explain the changes.** Tell the user what schema changes will be included.
4. **One migration per logical change.** Do not bundle unrelated schema changes.
5. **Configuration-only changes may not need migration.** If only EF metadata changed (index names, column order) without schema impact, ask if migration is needed.

**Forbidden:**
- Auto-generating migrations without confirmation
- Generic names: `Migration1`, `Update`, `Fix`, `Temp`
- Bundling multiple features in one migration
- Creating migrations for configuration-only changes without asking

## Migration Naming Convention

```
{YYYYMMDDHHMMSS}_{PascalCaseDescription}.cs
```

Always use `dotnet ef migrations add` (which auto-generates the timestamp). Example:

```bash
dotnet ef migrations add AddAuditLogging -p backend/src/Notrelix.Infrastructure -s backend/src/Notrelix.Api
```

## Critical Rule: Pre-deployment vs Post-deployment

Determine whether `SchemaV2Baseline` has been deployed to production.

### Pre-deployment (Baseline NOT deployed yet)

**DO NOT create new migration files.** Instead:
1. Modify the existing `20260702093805_SchemaV2Baseline.cs` directly (`Up()` method)
2. Modify `20260702093805_SchemaV2Baseline.Designer.cs` to match the model snapshot
3. Verify `ApplicationDbContextModelSnapshot.cs` already reflects the correct model

### Post-deployment (Baseline deployed to production)

Create a new migration following naming convention:

```bash
dotnet ef migrations add {DescriptiveName} -p backend/src/Notrelix.Infrastructure -s backend/src/Notrelix.Api
```

## Config Sync Rule

When any `*Configuration.cs` file is modified (e.g., `WorkspaceConfiguration.cs`), **all 3 files must be kept in sync**:

| File | Responsibility |
|------|----------------|
| `*Configuration.cs` | Source of truth for EF model |
| `{timestamp}_{name}.cs` (`Up()`) | DDL changes to apply |
| `{timestamp}_{name}.Designer.cs` | Model snapshot for EF diff engine |

When in doubt, regenerate:

```bash
dotnet ef migrations add TempCheck -p backend/src/Notrelix.Infrastructure -s backend/src/Notrelix.Api
```

Then inspect what changed. If nothing should change, delete the scratch migration.

## No Intermediate Fix Migrations

**Never create fix/patch migrations** like:
- `FixPersonalWorkspaceUniqueIndex`
- `PatchAccountId`
- `FixWorkspaceIndex`

If the baseline hasn't been deployed, modify it directly. If it has been deployed, make a properly named migration describing what changed (e.g., `AddAuditLogging`, `AddCustomEmailProvider`).

## Snapshot Rule

`ApplicationDbContextModelSnapshot.cs` is the authoritative snapshot of the current model. It must always:
- Match the combined effect of all applied migrations
- Be regenerated by `dotnet ef migrations add`, never hand-edited

If the snapshot is out of sync with configs:

```bash
# Option A: If no real changes pending
dotnet ef migrations remove -p backend/src/Notrelix.Infrastructure -s backend/src/Notrelix.Api

# Option B: If real changes exist
dotnet ef migrations add {DescriptiveName} -p backend/src/Notrelix.Infrastructure -s backend/src/Notrelix.Api
```

## Verification

After any migration change, run:

```bash
dotnet build backend/Notrelix.sln
dotnet test backend/Notrelix.sln
```

Verify no `PendingModelChangesWarning` at build time.

## Down Method

For baseline migrations, the `Down()` method drops entire tables — individual index changes in `Up()` don't need corresponding `Down()` entries.

For non-baseline migrations, always provide a proper `Down()` that reverses the `Up()` changes.
